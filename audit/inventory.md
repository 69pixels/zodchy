# Сводный инвентарь Ular × Spadafy (Z-012)

Дата: 2026-11-05. Основа: `audit/ular.md`, `audit/spadafy.md`, тема Graphical (`starter/theme-graphical/`). Это входные данные для стартера v0 (этап 3) и ретро-spec (этап 2).

Контекст проектов:

| | Ular | Spadafy |
|---|---|---|
| Статус | дизайн утверждён, есть мобильная версия, на проверке у клиента → **пилот** | десктоп не утверждён, мобильных макетов нет → **проверка переиспользуемости** |
| Языки | RU + KK + EN | только EN |
| База макета | 1440 | 1920 (сетка 12 × 135, gutter 20, margin 40) |
| Размеры в коде | `calc(N * var(--u))`, `--u = 100vw/1440` | то же, `--u = vw/1920` (из JS) |
| Шрифты | Aeonik + Roboto Mono | Review Condensed + Aeonik |
| Деплой | GitHub Pages | GitHub Pages |
| Страницы | 1 | главная + «The Tech» (нужна в v1) |

Оба проекта сделаны одним приёмом: линейное масштабирование от ширины макета, одна `scroll`-функция с расчётом прогресса, контент и разметка частично в JS. Это и есть основной «долг», который стартер должен убрать.

## 4. Токены стартера (из пересечений)

Что в обоих проектах повторяется и должно стать токенами темы:

- **Сетка и ритм:** поля 40 / 60 px, gutter 20 / 24, колонки 12; размеры по шкале, а не `calc(N * --u)`. Брейкпоинты 1440 / 1024 / 768 / 375; 1920 — только «широкий» режим для Spadafy.
- **Цвета (общая роль → значения по проектам):** `ink`, `grey`, `soft`, `accent`, `accent-hover`, `surface-dark`, `error`; Ular: оранжевый `#ff4600` + жёлтый; Spadafy: розовый `#fc029c` + оранжевый `#ff521d` + графит.
- **Типографика:** роли `display`, `body`, `mono/eyebrow`; у проектов разные шрифты.
- **Радиусы:** пилюля (999), 20/24/28/32 — свести к шкале (`sm`, `md`, `lg`, `pill`).
- **Движение:** `--ease-out`, `--ease-io` (у Spadafy уже вынесены), длительности 200 / 260 / 320 / 450 мс, лимиты задержек для `data-motion-delay`.
- **Темы:** `wireframe` (серая, без брендовых шрифтов) → `brand` (из проекта). Graphical-тема лежит между ними как источник атомов.

## 5. Общие проблемы, которые стартер обязан исправить

1. Размеры от ширины экрана (`--u`) вместо шкал и брейкпоинтов.
2. Контент и разметка секций в JS (SEO, первая отрисовка, no-JS). В Astro — серверный рендер и контент-коллекции.
3. Прогресс скролла считается вручную в `scroll`-обработчике с чтением layout. Заменить на GSAP ScrollTrigger (решение принято).
4. Reduced motion: Ular — полностью, Spadafy — частично (JS-сцены и автопереход не отключаются). Правило библиотеки: у каждого пресета есть статичный фолбэк, проверяемый в QA.
5. Магические числа сцен → именованные параметры и `data-` атрибуты секции.
6. Ассеты без `srcset` и современных форматов; лицензии шрифтов не подтверждены (Aeonik — лицензия есть, файлы не переданы; Review Condensed — неизвестно).
7. Версий нет (история «Delete / Add files via upload») — в новом процессе ветки на версию.
8. Именование в Figma не по конвенции; раскадровки анимации есть только у Spadafy. Для стартера нужны правила `NN-Section / vN / desktop|mobile` и `motion / NN-Section / step-N`.

## 6. Рекомендации по порядку работ

1. **Z-020 ретро-spec Ular** первым: проект ближе к финишу, мобильная версия есть, 3 языка влияют на структуру контента.
2. **Z-030 стартер v0** строить сразу под Ular: Astro, токены (wireframe + brand), Graphical как источник атомов, i18n-каркас RU/KK/EN.
3. Секции из «первой очереди» собирать в процессе вёрстки Ular, а не заранее: тогда в библиотеку попадает проверенное (Z-031).
4. **Spadafy** — после утверждения десктопного дизайна: ретро-spec (Z-021) и вторая очередь библиотеки; проверка «стартер без доработок» на секциях, которые у него совпадают с Ular.
5. Рассматривать `scroll-pin/reveal` как главный риск: самые сложные сцены у обоих проектов, ядро пресета нужно спроектировать один раз (параметры: высота трека, фазы, источник прогресса).
