# HANDOFF — с чего начат Zodchy

Документ фиксирует контекст и решения из стартового обсуждения (05.11.2026), чтобы любая новая сессия агента начинала с них.

## Как работаем сейчас

- Дизайн и прототипы — в Figma. Часто несколько вариантов одной секции (карточки / пагинация / скролл / анимация / просто текст).
- До утверждения дизайна обычно нет дизайн-системы и компонентов; после — текстовые и цветовые стили и несколько атомов (кнопки, хедер, меню, поля). Макеты по колоночной сетке.
- Кликабельные HTML-прототипы делаем с ИИ (Claude Code / Codex): агент читает Figma по ссылке, навигацию и анимации описываем текстом в свободной форме.
- Вёрстка — Webflow; переходим на кастомную вёрстку ИИ + Astro. Пока только одностраничные лендинги без CMS и сторонних сервисов.
- Часто нет ТЗ от клиента — пишем его сами.

## Проблемы

1. Прототипы никуда дальше не идут, вёрстка делается заново.
2. Нет дизайн-системы, примеров секций и анимаций.
3. Нет единого пайплайна.
4. Figma MCP съедает много токенов.
5. Нет бэклога, правки часто без отката, версии создаются вручную по просьбе.

## Корневая причина

Нет промежуточного слоя между Figma и кодом. Знания проекта живут в Figma и в чате, а не в репозитории — агент каждый раз собирает сайт с нуля.

## Решения

1. **Прототип = первая версия продакшна.** Один Astro-репозиторий на проект; low-fi → hi-fi → прод — смена темы и наполнения, а не переписывание.
2. **Студийный стартер** с четырьмя слоями: токены (wireframe + brand из Graphical) → атомы (Graphical / Base UI, React-острова) → библиотека секций с вариантами → библиотека анимаций-пресетов. Плюс каталог `/library`.
3. **Spec вместо свободного текста и вместо отсутствующего ТЗ:** `spec/site.md` + файл на секцию (шаблоны в `templates/spec/`). Spec — главная ручная точка работы человека.
4. **Figma: выгрузить один раз и закэшировать** в `design/`; конвенции именования фреймов; стили/переменные даже на черновиках; позже Code Connect для атомов.
5. **Агенты по ролям** (см. `AGENTS.md`), вводятся постепенно; QA — обязательно в отдельном контексте.
6. **Git с первой минуты**, ветка на версию, preview-деплой на ветку, варианты секций переключаются прямо в прототипе (review-панель или `?section=variant`). Бэклог — GitHub Issues, `DECISIONS.md` в каждом проекте.
7. **Harvest:** после каждого проекта новое уходит в стартер.

Ресурс: Graphical (graphicalui.com) — конструктор темы, 5 стилей, React-компоненты на Base UI, `GUI.md` с токенами, навыки для кодинг-агентов, установка через shadcn.

## План запуска

1. **Аудит Ular и Spadafy** — код прототипов + Figma (метаданные и скриншоты). Инвентарь секций, вариантов, анимаций, повторяющихся атомов, костылей.
2. **Ретро-spec** для обоих проектов — заменяет ТЗ; дальше вёрстка по нему.
3. **Стартер v0** — из пересечений двух проектов + тема Graphical.
4. **Пилот** — проект, ближе к утверждению дизайна, верстается в Astro по новому процессу; второй проверяет переиспользуемость стартера.

## Рекомендации (ждут подтверждения)

- **Бэклог → GitHub Issues.** Репозитории уже на GitHub, задачи связываются с ветками и PR, агенты (Claude Code, Codex) работают с ними через `gh`. Linear имеет смысл, если нужны клиентские/продуктовые доски, чего пока нет.
- **Анимации → GSAP + ScrollTrigger.** Секции Astro в основном без React, а пресеты подключаются атрибутами `data-motion` — это ванильный JS, где GSAP на месте. Motion заточен под React-компоненты. Простые reveal'ы — на CSS/IntersectionObserver, GSAP только для таймлайнов и скролл-сцен.
- **Хостинг → оставить GitHub Pages для первых превью, к пилоту перейти на Cloudflare Pages.** Pages держит один сайт на репозиторий, поэтому превью на каждую ветку (`v2-…`, `review/…`) не получится; Cloudflare Pages даёт бесплатный URL на каждую ветку и закрытие превью паролем.
